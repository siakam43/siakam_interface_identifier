## Overview

You are executing the SIAKAM Interface Identifier skill. Your goal is to identify which functions in a C project are "external interfaces" — functions that serve as communication entry points for external users or external modules, particularly those that receive untrusted external data.

You work exclusively through LLM-driven code review and parallel subagents. You MUST NOT write or execute any scripts or code. All analysis is done by reading source files and using grep.

This skill is invoked via:

```

- Read all source files under `project_dir` (including `.c`, `.h`, `.S`, `.lds` files)

# Step 1: Project Architecture Analysis Prompt

You are analyzing a C project to identify its architecture. Your output will be used by parallel subagents as shared context for classifying candidate functions. Be thorough but concise.

The analysis must cover the following four sections in order.

## 1. Module Composition and Boundaries

Explore the top-level directory structure of the project. For each sub-directory that represents a distinct sub-module:

- Its path relative to `project_dir`
- Its purpose (1-2 sentences, inferred from file naming, Makefile/Kbuild, or header comments)
- Which public headers it exposes (files under an `include/` directory or headers referenced by other modules)

Focus on what a developer external to this sub-module needs to know to use it. Ignore internal implementation details.

## 2. External Framework / Subsystem Dependencies

Identify which kernel frameworks or external subsystems the project depends on. For each dependency:

- The framework name (e.g., Linux I2C subsystem, SPI bus, PCI, UEFI Boot Services, HarmonyOS HDF)
- How the project registers with it — look for:
  - `*_driver_register()` calls
  - `module_init()` / `module_exit()` macros
  - `class_create()` / `device_create()` calls
  - `uefi_driver_register()` or equivalent UEFI entry points
  - `HdfDriverEntry` or equivalent HarmonyOS HDF entry points
- What entities this project registers (e.g., a `struct platform_driver`, a `struct i2c_driver`)

Search for these patterns with grep:

```
grep -rn "module_init\|module_exit" --include="*.c"
grep -rn "_driver_register\|_driver_unregister" --include="*.c"
grep -rn "class_create\|device_create\|sysfs_create" --include="*.c"
grep -rn "proc_create\|debugfs_create\|register_sysctl" --include="*.c"
grep -rn "register_.*_notifier" --include="*.c"
grep -rn "EFI_SERVICE_BINDING\|EFI_DRIVER_BINDING" --include="*.c" --include="*.h"
grep -rn "HdfDriverEntry\|HDF_DRIVER" --include="*.c" --include="*.h"
```

## 3. Typical Interface Registration Patterns

Identify the callback tables and registration structures used in this project. For each pattern found:

- The struct type (e.g., `struct file_operations`, `struct i2c_algorithm`, `struct platform_driver`)
- Where it is defined and registered (file path and approximate line)
- Which functions of this project are assigned as callbacks (if visible at this stage)

Search for these patterns with grep:

```
grep -rn "struct file_operations\|struct device_attribute\|struct attribute_group" --include="*.c"
grep -rn "struct i2c_driver\|struct spi_driver\|struct pci_driver\|struct platform_driver" --include="*.c"
grep -rn "struct usb_driver\|struct usb_class_driver" --include="*.c"
grep -rn "struct proto_ops\|struct netlink_kernel_cfg" --include="*.c"
grep -rn "static.*struct.*_ops\b" --include="*.c"
```

## 4. Module Communication Topology

Describe how the sub-modules interact with external entities:

- Which sub-module talks to which external framework/subsystem
- Through what mechanism (ioctl, sysfs, proc, netlink, driver probe, interrupt, etc.)
- The direction of data flow (inbound → receives external data, outbound → sends data out, or bidirectional)

Produce this as a simplified text diagram or bullet list. Example:

```
Module: drivers/foo/
  → Linux VFS (userspace) via file_operations (ioctl, read, write) [bidirectional]
  → I2C bus via i2c_driver.probe [inbound — hardware enumeration]
  → Internal to module bar/ via direct function call

Module: drivers/bar/
  → Platform bus via platform_driver [inbound — device tree match]
```

## Output

Write your complete analysis to `.siakam_out/SII/arch.md`. Use clear markdown headings. Keep the total between 200-400 lines.
```

```markdown
# Step 3: Per-Group Function Analysis Prompt

You are a subagent in the SIAKAM Interface Identifier analysis. You are assigned ONE group of candidate functions to analyze. Your job is to determine, for each function in your group, whether it is an "external interface" — a function that serves as a communication entry point for external users or external modules, particularly one that receives untrusted external data.

## 1. Setup

Read these files before starting:
- `.siakam_out/SII/arch.md` — the project architecture analysis (shared context for all subagents)
- `.siakam_out/SII/tasks.md` — locate your group (Group NNN) and its function list

Your assigned functions are listed in the `tasks.md` table under your group. Note the group number `NNN` for the output path.

## 2. Recovery Check

Before beginning analysis, check if `.siakam_out/SII/results/group_NNN.json` already exists and contains more than `{}`. If it does, it means you are resuming from a prior crashed attempt. Read the existing results and resume from the first unanalyzed function (do NOT re-analyze functions already in the file).

## 3. Function Analysis Loop

For each candidate function in your group, perform the following steps in order.

### 3.0: Load Function Source

Read the function source at `file:line_start` from `entry.json`.

**If the source cannot be loaded** (file does not exist, line is out of range, function definition not at expected line):
- Record in results with `confidence: "error"` and reason `"function source not found at <file>:<line>"`
- These will be placed in the `failures` section of the final output
- Do NOT skip silently — the user needs to know about every unanalyzable function

Continue with the remaining steps only if the source was successfully loaded.

### 3.A: Quick Exclusion

Check if the function can be trivially excluded. A function is trivially excluded if ANY of these are true:

- The file path contains `test`, `mock`, `sample`, `example`, or `debug` as a path component
- The function name matches patterns `test_*`, `*_test`, `mock_*`, `stub_*`, `dummy_*`
- The function body is effectively empty: only a `return 0;`, `return;`, or a single no-op statement

If the function is trivially excluded, record the exclusion reason (e.g., `quick_exclusion_test_code`) and skip to the next function. Do NOT add trivially excluded functions to the results.

### 3.B: Search for Registration Points

Use `grep` to find all references to the function name in the project directory. Search for these registration patterns:

1. **Direct struct member assignment:** `.callback = func_name`, `.ioctl = func_name`, `.probe = func_name`, `.open = func_name`, `.read = func_name`, `.write = func_name`, etc.
2. **Static array element:** The function name appears inside `static const struct ... [] = { ... }` array initialization
3. **Indirect struct member assignment:** `ops->func = func_name`, `driver->func = func_name`, `*ptr = func_name`
4. **Static function body registration:** The function name appears as an argument to registration APIs like `register_*()`, `*_add()`, `*_install()`
5. **Exported symbols:** `EXPORT_SYMBOL(func_name)` or `EXPORT_SYMBOL_GPL(func_name)`
6. **IRQ/timer/workqueue registration:** `request_irq(..., func_name)`, `request_threaded_irq(..., func_name)`, `timer_setup(&t, func_name, ...)`, `INIT_WORK(&w, func_name)`

**Grep commands to run (adapt function name as needed):**

```bash
grep -rn "\b<func_name>\b" --include="*.c" --include="*.h" --include="*.S"
```

Read the context around each match to determine which registration pattern (if any) it represents. A function name may appear in comments, string literals, or forward declarations — these are NOT registration points and should be ignored.

### 3.C: Classify Registration Pattern

Based on the registration points found, classify whether this is an external interface:

**External interface** — the function is registered with one of these frameworks:
- Userspace-facing: `file_operations`, `sysfs_ops`, `netlink_ops`, `proto_ops`
- Kernel framework driver: `platform_driver.probe/remove/suspend/resume`, `i2c_driver.probe`, `spi_driver.probe`, `pci_driver.probe`
- UEFI: `EFI_SERVICE_BINDING`, `EFI_DRIVER_BINDING_PROTOCOL`
- HarmonyOS HDF: `HdfDriverEntry.Bind/Init/Release`
- `/proc`, `/sys`, debugfs, sysctl: `proc_create`, `sysfs_create_file`, `debugfs_create_file`, `register_sysctl_table`
- Notifier chain: `register_*_notifier`, `atomic_notifier_chain_register`, `blocking_notifier_chain_register`

**External interface (conditional)** — requires additional judgment:
- IRQ handler (`request_irq`, `request_threaded_irq`):
  - **External interface** if the IRQ is triggered by external hardware or an off-chip source
  - **Exclude** if the IRQ is purely internal (on-chip IP block handled entirely within the driver)
  - You MUST analyze the IRQ number/source. Search for the interrupt specifier (device tree `interrupts` property, IRQ number definition, or hardware documentation comments) to determine the source.

**Exclude** — the registration is internal:
- Timer/workqueue callback (`timer_setup`, `INIT_WORK`, `schedule_work`): these are internal kernel scheduling mechanisms
- Internal-only callback: the function is referenced by a struct/array that is only used within the same module (e.g., passed to a function defined in the same file or a closely related file in the same sub-module)

**No registration point found** → Proceed to Step 3.D.

### 3.D: Further Analysis for Functions with No grep Results

When `grep` finds no references to the function name, do NOT automatically mark it as dead code. Registration or linkage may be invisible to grep (e.g., linker scripts, external build systems, runtime dispatch tables built by macros).

Perform the following analysis:

1. **Analyze the function signature and parameters:**
   - Does it receive pointer parameters that could originate externally? (e.g., `struct device *`, `void __user *`, `const char *`, hardware register addresses)
   - Does its signature match common interface patterns? (e.g., `int (*)(struct device *, ...)`, `ssize_t (*)(struct file *, const char __user *, size_t, loff_t *)`)

2. **Analyze what the function does with its inputs:**
   - `copy_from_user()`, `get_user()`, `__get_user()` calls → likely userspace interface
   - Hardware register reads (`readl()`, `ioread32()`, `inb()`) → likely hardware interface
   - Parsing structured data (TLV, network packets, configuration formats) → likely external interface
   - Pure computation on internal state with no external input → likely internal helper

3. **Check function naming conventions:**
   - Does the name match known interface suffixes: `*_handler`, `*_callback`, `*_irq`, `*_isr`, `*_entry`, `*_ioctl`, `*_open`, `*_release`, `*_probe`, `*_init`, `*_exit`?

4. **Check surrounding code context:**
   - Is this function defined in a file whose other functions are confirmed external interfaces?
   - Is it in a translation unit that corresponds to a public API boundary (e.g., `api.c`, `interface.c`, `ops.c`)?

5. **Check for macro-based registration:**
   - If the function name follows a pattern (e.g., `foo_open`, `foo_ioctl`, `foo_probe`), grep for the stem/prefix in macro invocations. Look for patterns like `DECLARE_OPS(foo)`, `DEFINE_DRIVER(foo)`, `REGISTER(foo)` that might construct the registration via token pasting (`##`).

**Decision:**
- If implementation analysis suggests the function is an external interface → Record as `medium` confidence, with analysis note: "no registration point found, identified by implementation analysis"
- If truly unreferenced and implementation shows no interface characteristics → **Exclude** (record reason: `no_registration_no_interface_characteristics`)
- If there are signs of macro-based registration that you cannot fully resolve → Record as `medium` confidence, note: "possible macro-based registration, manual review recommended"

### 3.E: Assign Confidence Rating

When recording a confirmed external interface, assign a confidence rating:

| Rating | Criteria |
|--------|----------|
| **high** | Registration pattern clearly maps to an external interface framework from Step 3.C, AND you can clearly describe the external data flow path from initiator to this function's parameters |
| **medium** | Registration pattern suggests external interface but the business context is not fully clear; OR the interface type is clear but the data flow path is complex or uncertain; OR identified by implementation analysis without a registration point |
| **low** | Some external interface characteristics but cannot confirm — DO NOT write to results. Exclude and record reason. |

## 4. Result Format

Write your results to `.siakam_out/SII/results/group_NNN.json` (replace NNN with your group number, zero-padded to 3 digits).

### 4.A: Progress Persistence

Every 5 functions, re-write the results file with the current state. This guards against mid-analysis crashes. Each write is a complete replacement of the file, containing ALL results analyzed so far (not just the new ones).

### 4.B: Result File Structure

```json
{
  "group": "module_A_1",
  "group_number": 1,
  "analyzed_at": "<ISO timestamp>",
  "functions_total": 28,

# Step 4: Result Merge Prompt

You are merging the results from parallel group analysis into the final `apis.json` output.

## 1. Load All Group Results

Read every `.siakam_out/SII/results/group_*.json` file. Sort them by group number.

Track groups that are missing (placeholder `{}` only) or incomplete — these are failures. For each, check if retries were exhausted.

## 2. Merge Interfaces

Collect all `interfaces` arrays from all group result files into a single list.

### Deduplication

Deduplicate by composite key: `file:name` (file path + function name). If the same `file:name` appears in multiple groups, keep the entry with the higher confidence rating. If confidences are equal, keep the later one (higher group number).

### Filtering

- EXCLUDE all entries with `confidence: "low"`. They are not confirmed external interfaces.
- KEEP entries with `confidence: "high"` or `confidence: "medium"`.
- PLACE entries with `confidence: "error"` into the `failures` array.

### Sorting

Sort the merged interfaces by module (extract the top-level directory from `file`), then by file path, then by line number.

## 3. Aggregate Statistics

### Exclusion Reasons

Sum the `exclusion_reasons` counts from each group result file into a single `summary.exclusion_reasons` object. If a reason appears in multiple groups, sum the counts.

### Interface Counts

Count `high_confidence` and `medium_confidence` entries separately for `summary`.

## 4. Partition Errors and Warnings

- **`errors`**: Runtime issues that affected result completeness. Includes:
  - Groups that failed after exhausting retries: `"group_NNN failed after 2 retries: <reason>"`
  - Groups with partially corrupted results

- **`warnings`**: Non-blocking data quality issues. Includes:
  - Empty entry.json (if applicable)
  - Functions that could not be located (from `failures`)

If there are no errors or warnings, use empty arrays `[]`.

## 5. Write Final Output

Write `.siakam_out/SII/apis.json` with this structure:

```json
{
  "project": "<project_dir basename>",
  "analysis_date": "<YYYY-MM-DD>",
  "total_candidates": <sum of all functions_total from all groups>,
  "confirmed_interfaces": <count of interfaces after filtering>,
  "summary": {
    "high_confidence": <count>,
    "medium_confidence": <count>,
    "exclusion_reasons": {
      "<reason_key>": <count>,
      ...
    }
  },
  "interfaces": [
    {
      "name": "<function name>",
      "file": "<relative path from project_dir>",
      "line": <line number>,
      "confidence": "<high or medium>",
      "analysis": "<multi-line analysis from group result>"
    },
    ...
  ],
  "failures": [
    {
      "name": "<function name>",
      "file": "<path>",
      "line": <line number>,
      "reason": "<failure reason>"
    },
    ...
  ],
  "errors": ["<error message>", ...],
  "warnings": ["<warning message>", ...]
}
