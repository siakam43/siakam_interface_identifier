# SIAKAM Interface Identifier Skill Design

## Overview

A pure markdown skill that identifies "external interfaces" in C projects (Linux kernel drivers, HarmonyOS kernel drivers, UEFI boot chain, firmware). External interfaces are functions defined within the project that serve as communication entry points for external users or external modules, particularly those that receive untrusted external data.

The skill is invoked via `/siakam_interface_identifier <project_dir>` and uses LLM-driven code review with parallel subagents — no scripts or code execution.

## File Structure

```
siakam_interface_identifier/
├── SKILL.md                          # Main orchestration prompt (entry point)
└── prompts/
    ├── step1-project-analysis.md     # Step 1: Project architecture analysis
    ├── step3-group-analysis.md       # Step 3: Per-group function analysis (subagent)
    └── step3-merge.md              # Step 3: Result merging
```

Runtime outputs (all under `.siakam_out/SII/`):

```
.siakam_out/
├── entry.json              # Input — pre-generated by a call-graph analysis tool
└── SII/
    ├── arch.md             # Step 1 output — project architecture analysis
    ├── state.json            # Execution state for resume (temporary, cleaned on success)
    ├── tasks.md            # Task tracking file (temporary)
    ├── results/            # Per-group intermediate results (temporary)
    │   ├── group_001.json
    │   ├── group_002.json
    │   └── ...
    └── apis.json           # Final output — confirmed external interfaces
```

## Process Flow

### Step 0: Parameter Parsing & Pre-checks

1. Parse `project_dir` argument, default to current directory.
2. If `--resume` flag is passed, check for `.siakam_out/SII/state.json` and skip to the last recorded step (see Resume Mechanism below).
3. Read `.siakamignore` if present, exclude matching paths (gitignore syntax).
4. Check that `.siakam_out/entry.json` exists; if not, prompt user to provide the entry.json file and abort.
5. Create `.siakam_out/SII/` and `.siakam_out/SII/results/` directories.

### Step 1: Project Architecture Analysis

LLM explores the project and produces `arch.md` containing:

1. **Module composition and boundaries**: Top-level directory structure, which subdirectories correspond to which sub-modules. Public header file paths.
2. **External framework/subsystem dependencies**: Which kernel frameworks or subsystems the project depends on (e.g., I2C, SPI, PCI, USB, UEFI Protocol, HDF). What types of entities the project registers with these frameworks.
3. **Typical interface registration patterns**: Registration actions found in init code (`module_init()`, `platform_driver_register()`, `class_create()`, `sysfs_create_group()`, etc.). Callback tables exposed to external modules (`struct file_operations`, `struct device_attribute`, `struct i2c_algorithm`, `EFI_SERVICE_BINDING`, `HdfDriverEntry`, etc.).
4. **Module communication topology**: A simplified dependency/communication map — which sub-modules interact with which external entities, through what mechanisms.

Target size: 200-400 lines of markdown. This provides shared context for all subagents in Step 3 without overwhelming their context window.

### Step 2: Parse entry.json & Create Task Groups

1. Read `entry.json` and extract the candidate function list.
2. If `entry_functions` array is empty, write an empty `apis.json` with `confirmed_interfaces: 0` and a note in `warnings` that no candidates were provided, then terminate. Skip Steps 1, 3, and 4.
3. Group functions by module based on file path, mapped to sub-modules identified in Step 1.
4. Group size limit: 30 functions per group. Oversized groups are split by sub-directory. If a sub-directory split still produces a group exceeding 30, split iteratively by file.
5. If total candidates ≤ 10, a single group is created.
6. Create `tasks.md` to track all groups.

### Step 3: Parallel Analysis (Core)

The main agent dispatches parallel subagents, each handling one group.

**Subagent workflow:**

1. Load `step3-group-analysis.md` prompt.
2. Read `arch.md` for global background context.
3. For each candidate function in the group, first attempt to locate and read the function source at `file:line_start`. If the file does not exist, the line is out of range, or the function cannot be located, record the function with `confidence: "error"` and reason `"function source not found at <file>:<line>"`. These entries are included in the final results under a separate `failures` section. Do NOT silently skip them.
   
   For each successfully loaded function, proceed with:

   **A. Quick exclusion:**
   - File path matches `*test*`, `*mock*`, `*sample*`, `*example*`, `*debug*`
   - Function name matches `test_*`, `_test`, `mock_*`, `stub_*`, `dummy_*`
   - Function body is empty or only `return 0;` / `return;`

   **B. Search for registration points** — grep the function name in the codebase, looking for:
   1. Direct struct member assignment: `.callback = func_name`, `.ioctl = func_name`
   2. Static array element: `static const struct ops arr[] = { { .init = func_name }, ... }`
   3. Indirect struct member assignment: `ops->func = func_name`, `driver->func = func_name`
   4. Static function body registration: `register_*(&func_name)`, `*_add(func_name)`, `*_install(func_name)`
   5. Exported symbols: `EXPORT_SYMBOL(func_name)`, `EXPORT_SYMBOL_GPL(func_name)`
   6. IRQ/timer/workqueue registration: `request_irq(..., func_name)`, `INIT_WORK(&w, func_name)` — typically excluded unless externally triggerable

   **C. Determine if registration pattern indicates external interface:**
   - Userspace-facing registration (`file_operations`, `sysfs_ops`, `netlink_ops`, `proto_ops`) → **External interface**
   - Kernel framework driver registration (`platform_driver.probe`, `i2c_driver.probe`, `spi_driver.probe`, `pci_driver.probe`) → **External interface**
   - UEFI protocol/service registration (`EFI_SERVICE_BINDING`, `EFI_DRIVER_BINDING_PROTOCOL`) → **External interface**
   - HarmonyOS HDF driver registration (`HdfDriverEntry.Bind/Init/Release`) → **External interface**
   - `/proc`, `/sys`, debugfs, and sysctl registration (`proc_create`, `sysfs_create_file`, `debugfs_create_file`, `register_sysctl_table`) → **External interface**
   - Notifier chain registration (`register_*_notifier`, `atomic_notifier_chain_register`, `blocking_notifier_chain_register`) → **External interface**
   - IRQ handler registration (`request_irq`, `request_threaded_irq`) → **External interface** if the IRQ is triggered by external hardware or an off-chip source. **Exclude** if the IRQ is purely internal (on-chip IP block handled entirely within the driver) — this requires LLM analysis of the IRQ source.
   - Timer/workqueue registration (`timer_setup`, `INIT_WORK`, `schedule_work`) → **Exclude** (these are internal kernel scheduling mechanisms, not external communication entry points)
   - Internal-only callback reference → **Exclude**
   - No registration point found → Proceed to D

   **D. Further analysis for functions with no grep results:**

   When grep finds no references to the function name, do NOT assume it is dead code. Registration or linkage may be invisible to grep (e.g., linker scripts, external build systems, runtime dispatch tables). In this case, analyze the function's implementation to determine intent:

   1. **Analyze function signature and parameters**: What data does the function receive? Are there pointers from external sources (e.g., `struct device *`, `void __user *`, `const char *`, hardware registers)? Trace where these parameters could originate.
   2. **Analyze what the function does with its inputs**: Does it copy from userspace? Read from hardware? Parse structured data? These behaviors suggest external interface.
   3. **Check function naming conventions**: Does the name match common interface patterns (e.g., `*_handler`, `*_callback`, `*_irq`, `*_isr`, `*_entry`)?
   4. **Check surrounding code context**: Is the function defined in a file whose other functions are confirmed external interfaces? Is it in a translation unit that clearly exposes APIs?

   - If implementation analysis suggests external interface → Record with `medium` confidence, noting "no registration point found, identified by implementation analysis"
   - If truly unreferenced and implementation shows no interface characteristics → **Exclude** (likely dead code or internal helper)
   - Interrupt handlers (`request_irq(` + function name) and initcall/exitcall patterns (`module_init(`, `*_initcall(`) that grep missed due to macro indirection → Continue to follow up with manual macro inspection

   **E. Confidence rating:**
   - **high**: Registration pattern clearly maps to an external interface framework, and LLM can clearly describe the external data flow path
   - **medium**: Registration pattern suggests possible external interface but business context is unclear; or interface type is clear but data flow is complex
   - **low**: Some external interface characteristics but cannot confirm — not written to apis.json

4. Write results to `SII/results/group_NNN.json`. Each group result includes its determined interfaces AND an `exclusion_reasons` summary for the group. Do NOT modify `tasks.md` — writing the result file is the only completion signal.

**Progress persistence:** The subagent writes a progress summary every 5 functions to guard against mid-analysis crashes.

**Crash recovery:** When a subagent starts, it checks whether its `results/group_NNN.json` contains partial results (from a prior crashed attempt). If so, it reads the existing results and resumes from the first unanalyzed function, avoiding duplicate work.

### Step 4: Merge Results

1. Verify all group result files in `results/` are non-empty JSON (complete).
2. Read all `results/group_*.json` files.
3. Merge and deduplicate by `file:name` as the composite key (functions with identical file path and name are the same entry; keep the later analysis). Sort by module.
4. Exclude `low` confidence entries. Aggregate exclusion reason counts into `summary.exclusion_reasons` from each group's results.
5. Partition runtime failures (group analysis errors, retries exhausted) into `errors`. Place data quality issues (empty input, missing files) into `warnings`.
6. Write final `apis.json`.
6. Clean up `tasks.md`, `results/` directory, and `state.json`.

## Task Tracking & Parallel Execution

### tasks.md Format

Managed exclusively by the main agent (subagents do not access it). Used to plan groups in Step 2 and track dispatch progress.

```markdown
## SIAKAM Interface Analysis Tasks

Total groups: N | Completed: 0 | In progress: 0 | Pending: N

| # | Status | Group | Functions | File Path | Result |
|---|--------|-------|-----------|-----------|--------|
| 1 | pending | module_A_1 | 30 | drivers/foo/ | - |
| 2 | pending | module_A_2 | 22 | drivers/foo/ | - |
| 3 | pending | module_B_1 | 18 | drivers/bar/ | - |
```

### Execution Rules

1. Main agent reads `tasks.md` to determine which groups are unassigned (no corresponding `results/group_NNN.json` exists).
2. Main agent dispatches subagents only for unassigned groups, providing each with its group name and function list directly (not via tasks.md). At dispatch time, main agent creates an empty `results/group_NNN.json` placeholder to prevent double-assignment.
3. Subagents write their full results to `results/group_NNN.json`. Subagents do NOT read or write `tasks.md` — this avoids file-level race conditions when multiple subagents finish simultaneously.
4. Main agent checks progress by listing `results/` directory: a group is complete when its result file is non-empty JSON (not just the placeholder). No polling of `tasks.md` status required.
5. When all result files are complete, proceed to merge.

### Progress Visibility

The main agent reports progress to the user each time it polls the `results/` directory:

```
[SIAKAM] Status: 5/18 groups complete | 3 in progress | 2 pending
```

This keeps the user informed during long-running analyses without flooding the output.

### Resume Mechanism

To survive session disconnections during long runs, the skill writes a lightweight `state.json` file at the start of each step:

```json
{
  "step": 3,
  "project_dir": "/path/to/project",
  "total_candidates": 872,
  "total_groups": 18,
  "groups_analyzed": 5,
  "started_at": "2026-05-18T10:30:00"
}
```

On invocation with `--resume`, the skill reads `state.json` and skips to the recorded step. For Step 3, it reads the existing `tasks.md` and `results/` directory to determine which groups still need analysis, avoiding re-analysis of completed groups.

### Fault Tolerance

1. A group is considered failed if its result file remains a placeholder (empty or incomplete JSON) after the subagent times out.
2. Before merging, main agent identifies failed groups by checking which result files are still incomplete. It re-dispatches each failed group with a fresh subagent.
3. Maximum 2 retries per group. If still failing after retries, record the failure in apis.json `errors` field.
4. Single group timeout: 15 minutes.

## Output Format: apis.json

```json
{
  "project": "project_dir_name",
  "analysis_date": "2026-05-18",
  "total_candidates": 872,
  "confirmed_interfaces": 156,
  "summary": {
    "high_confidence": 98,
    "medium_confidence": 58,
    "exclusion_reasons": {
      "quick_exclusion_test_code": 120,
      "quick_exclusion_empty_body": 15,
      "internal_callback_only": 380,
      "no_registration_no_interface_characteristics": 201
    }
  },
  "interfaces": [
    {
      "name": "foo_ioctl",
      "file": "drivers/foo/core.c",
      "line": 234,
      "confidence": "high",
      "analysis": "interface_type: ioctl_handler\nregistration: file_operations.unlocked_ioctl at drivers/foo/core.c:890\nexternal_module: Linux VFS / userspace\ndata_flow: userspace → ioctl(fd, cmd, arg) → foo_ioctl(struct file *, unsigned int, unsigned long)\n\nRegistered in struct file_operations.unlocked_ioctl, exposed to userspace via device node. The arg parameter carries a userspace pointer, making this an untrusted data entry point."
    }
  ],
  "failures": [
    {
      "name": "old_handler",
      "file": "drivers/foo/removed.c",
      "line": 100,
      "reason": "function source not found at drivers/foo/removed.c:100"
    }
  ],
  "errors": ["group_015 failed after 2 retries: unable to parse source"],
  "warnings": ["entry.json contained 0 candidates"]
}
```

Required fields per interface: `name`, `file`, `line`, `confidence`.
Analysis details are consolidated in the `analysis` field as multi-line text. Sub-fields MUST use the exact key names below so downstream consumers can parse them reliably:

- `interface_type:` — one of the recognized types (e.g., `ioctl_handler`, `sysfs_handler`, `netlink_handler`, `platform_driver_probe`, `i2c_driver_probe`, `spi_driver_probe`, `pci_driver_probe`, `uefi_protocol`, `hdf_driver`, `proc_handler`, `debugfs_handler`, `sysctl_handler`, `notifier_callback`, `exported_symbol`, `callback_table_entry`)
- `registration:` — registration pattern and code location
- `external_module:` — the external module or subsystem communicating via this interface
- `data_flow:` — external data inflow path (keep concise, one line)

Follow each key with a colon and space, one key per line. The `registration:` value MUST include a file:line location when the registration point is known. After these structured keys, a blank line separator followed by 1-2 sentences of free-text analysis is OPTIONAL but recommended.

## Orchestration Rules (SKILL.md)

### Required Permissions

- Read all source files under `project_dir`
- Use `grep` within `project_dir`
- Read/write `.siakam_out/SII/` directory
- Create subagents for parallel analysis

### Control Rules

1. Execute steps 0→1→2→3→4 strictly in order, no skipping.
2. After Step 1, `arch.md` must be written to disk before proceeding.
3. During Step 3, the main agent dispatches subagents for unassigned groups (using placeholder files to prevent double-assignment) and polls `results/` directory for completeness. It must not modify any result files while subagents are running.
4. Subagents may only write to `SII/results/group_NNN.json`. They must not modify other files.
5. If `tasks.md` shows abnormal status (timeout), report to user, preserve intermediate results, do not force-merge.

### Subagent Isolation

Each subagent can:
- Read `project_dir` source code
- Read `.siakam_out/SII/arch.md`
- Grep symbols within `project_dir`
- Write `.siakam_out/SII/results/group_NNN.json`

Each subagent cannot:
- Modify or read other groups' result files
- Modify `arch.md`, `entry.json`, or `tasks.md`

## Key Design Decisions

1. **Module-based grouping (Option C)**: Functions are grouped by sub-module to share business context, with secondary splitting by directory when groups exceed 30 functions.
2. **No coarse pre-filter stage**: Beyond trivial exclusions (test files, empty functions), all filtering is done during deep analysis to avoid false dismissals.
3. **Comprehensive registration patterns**: Covers struct member and static array assignment, indirect assignment, static init body registration, exported symbols, IRQ/timer registrations, proc/debugfs/sysctl entries, notifier chains, and macro-based registration detection.
4. **Confidence-based exclusion**: Only high/medium confidence results are written to the final output; low confidence entries are discarded to keep downstream security review focused.
5. **English prompts throughout**: All skill prompts are written in English.
