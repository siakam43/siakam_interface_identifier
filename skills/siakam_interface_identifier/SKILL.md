# SIAKAM Interface Identifier

## Overview

You identify which functions in a C project are "external interfaces" — functions serving as communication entry points for external users or external modules, particularly those that receive untrusted external data.

You work exclusively through LLM-driven code review and parallel subagents. You MUST NOT write or execute any scripts or code.

## Required Permissions

- Read all source files under `project_dir` (`.c`, `.h`, `.S`, `.lds`)
- Execute `grep` within `project_dir`
- Read and write files under `.siakam_out/SII/`
- Create subagents for parallel analysis

## Process

Execute these steps in strict order:

1. **Step 0**: Parse parameters and validate inputs
2. **Step 1**: Analyze project architecture → produce `.siakam_out/SII/arch.md`
3. **Step 2**: Parse `entry.json` and create task groups → produce `.siakam_out/SII/tasks.md`
4. **Step 3**: Dispatch parallel subagents to analyze each group → produce `.siakam_out/SII/results/group_*.json`
5. **Step 4**: Merge results → produce `.siakam_out/SII/apis.json` and clean up temporary files

Report a brief summary after each step. Never skip a step unless explicitly instructed below.

---

## Step 0: Parameter Parsing & Pre-checks

1. Set `project_dir` to the user-provided argument, or the current working directory if not specified.
2. If `--resume` flag is present, skip to the **Resume** section at the bottom of this document.
3. Read `.siakamignore` in `project_dir` if it exists. Parse using gitignore syntax. All paths matching these patterns MUST be excluded from subsequent grep searches and file reads.
4. Check that `.siakam_out/entry.json` exists. If not, output:

   ```
   [SIAKAM] ERROR: .siakam_out/entry.json not found in <project_dir>.
   Please provide the entry.json file generated by a call-graph analysis tool and try again.
   Expected format:
   { "entry_functions": [ { "name": "...", "file": "...", "line_start": N }, ... ] }
   ```

   Then STOP.

5. Create directories: `.siakam_out/SII/` and `.siakam_out/SII/results/`.
6. Write `.siakam_out/SII/state.json`:

   ```json
   { "step": 0, "project_dir": "<project_dir>", "started_at": "<ISO timestamp>" }
   ```

7. Report: `[SIAKAM] Step 0 complete. Project: <project_dir>. Starting architecture analysis...`

Proceed immediately to Step 1.

---

## Step 1: Project Architecture Analysis

1. Read the prompt file `prompts/step1-project-analysis.md` located relative to this SKILL.md. Follow its instructions exactly.

2. Update `state.json` with `"step": 1`.

3. Explore the project and produce `.siakam_out/SII/arch.md`.

4. Verify arch.md covers all 4 required sections: module composition, external framework dependencies, registration patterns, communication topology. Target 200-400 lines.

5. Report: `[SIAKAM] Step 1 complete. Architecture analysis saved to .siakam_out/SII/arch.md.`

Proceed immediately to Step 2.

---

## Step 2: Parse entry.json & Create Task Groups

1. Read `.siakam_out/entry.json`. Extract the `entry_functions` array.

2. **If `entry_functions` is empty**, write an empty `apis.json` and terminate:

   ```json
   {
     "project": "<project_dir_name>", "analysis_date": "<YYYY-MM-DD>",
     "total_candidates": 0, "confirmed_interfaces": 0,
     "summary": { "high_confidence": 0, "medium_confidence": 0, "exclusion_reasons": {} },
     "interfaces": [], "failures": [], "errors": [], "warnings": ["entry.json contained 0 candidates. No analysis performed."]
   }
   ```
   Report: `[SIAKAM] WARNING: entry.json contains 0 candidates. Empty apis.json written.` STOP.

3. Group functions by module (map file paths to sub-modules from arch.md). Functions not matching any module go into a group named after their parent directory.

4. **Group size limit: 30 functions maximum.** Split oversized groups by sub-directory. If still >30, split by file alphabetically.

5. If total candidates ≤ 10, create a single group.

6. Create `.siakam_out/SII/tasks.md` (managed EXCLUSIVELY by you):

   ```markdown
   ## SIAKAM Interface Analysis Tasks
   Total groups: N | Dispatched: 0 | Complete: 0 | Pending: N
   | # | Status | Group | Functions | File Path | Result |
   |---|--------|-------|-----------|-----------|--------|
   | 1 | pending | module_A_1 | 28 | drivers/foo/ | - |
   ```

   Status values: `pending`, `dispatched`, `complete`, `failed`.

7. Update `state.json` with `"step": 2`, `"total_candidates"`, `"total_groups"`, `"groups_completed": 0`.

8. Report: `[SIAKAM] Step 2 complete. <N> candidates in <M> groups (max 30/group). Starting parallel analysis...`

Proceed immediately to Step 3.

---

## Step 3: Parallel Analysis

### 3.1 Dispatch Loop

Repeat until all groups in `tasks.md` are `complete` or `failed`:

1. For each `pending` group in `tasks.md`:
   a. Create placeholder: write `{}` to `.siakam_out/SII/results/group_NNN.json` (NNN = group number, zero-padded to 3 digits).
   b. Update status to `dispatched` in tasks.md.
   c. Dispatch a subagent with these exact instructions:

   ```
   Read prompts/step3-group-analysis.md (relative to .omc/skills/siakam_interface_identifier/).
   Read .siakam_out/SII/arch.md for architecture context.
   Your group is NNN: <group_name>. Function list is in .siakam_out/SII/tasks.md.
   Follow step3-group-analysis.md EXACTLY.
   Write results to .siakam_out/SII/results/group_NNN.json.
   Do NOT modify tasks.md, arch.md, or other result files.
   Output: "[SIAKAM] Group NNN complete: X interfaces, Y excluded."
   ```

2. Wait briefly (30-60 seconds), then check `results/` directory. A group is complete when its file is non-empty JSON (not `{}`).

3. Update tasks.md and state.json. Report progress:

   ```
   [SIAKAM] Status: <complete>/<total> groups done | <dispatched> in progress | <pending> remaining
   ```

### 3.2 Fault Tolerance

- A group is **failed** if its result file is still `{}` or empty after 15 minutes.
- Delete the placeholder, reset status to `pending`, retry up to 2 times.
- If still failing after 2 retries, mark `failed` in tasks.md. Record for Step 4 errors.

### 3.3 Completion

When all groups are `complete` or `failed`, report:

```
[SIAKAM] Step 3 complete. <X>/<M> groups succeeded, <Y> failed.
```

Proceed to Step 4.

---

## Step 4: Merge Results

1. Verify all `results/group_*.json` files are non-empty JSON.

2. Read the prompt file `prompts/step3-merge.md` and follow it exactly.

3. Clean up temporary files: `tasks.md`, `results/` directory, `state.json`.

4. Report final results:

   ```
   [SIAKAM] Analysis complete.
     Candidates: <N> | Confirmed interfaces: <X> (high: <H>, medium: <M>) | Excluded: <Y> | Failures: <F>
     Output: .siakam_out/SII/apis.json
   ```

STOP. Skill complete.

---

## Resume Mechanism

When `--resume` is passed:

1. Read `.siakam_out/SII/state.json`. If missing, report: `[SIAKAM] No state.json found. Run without --resume.` STOP.

2. Based on `state.json` step:
   - **0 or 1**: Re-run from Step 1.
   - **2**: Re-run from Step 2.
   - **3**: Skip to Step 3. Check `tasks.md` vs `results/`: groups with non-empty result files are `complete`, empty/placeholder files reset to `pending`.
   - **4**: Skip to Step 4.

3. Resume from the indicated step.

---

## Critical Rules

1. Steps are sequential. Never skip unless: empty entry.json (terminate early), or `--resume`.
2. Subagents write ONLY to `results/group_NNN.json`. They MUST NOT touch tasks.md, arch.md, or other groups.
3. You (main agent) are the ONLY entity writing to tasks.md, state.json, and apis.json.
4. Mandatory progress report after each step and during Step 3 dispatch cycles.
5. On user interrupt, save state to state.json for `--resume` recovery.
6. All analysis by reading source and grep. NO scripts. NO code execution.
7. All file paths in output MUST be relative to `project_dir` (not absolute paths).
